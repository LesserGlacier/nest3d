# nest3d

## Measure on the real parts, not the samples

`examples/sample_parts/*.step` are generated by `tests/make_samples.py` out of
OCC primitives. They exist so the pipeline can be exercised anywhere, and they
are the right thing for correctness tests. **They are the wrong thing for any
measurement**: they are stubby and do not nest, so they understate what the
settle earns (2.43 density points against 3.80 on the real parts) and pack to a
different regime entirely (41-45% against 47-54%).

Every benchmark and every tool here takes `--parts`, defaulting to the glob in
**`$NEST3D_PARTS`** and falling back to the samples when it is unset. That
fallback is silent, so a session that forgets to set it will quietly measure the
wrong geometry and report conclusions that do not transfer.

The real path is machine-specific and confidential, so it is not committed. It
lives in **`local.env`** (gitignored) next to this file. Source it, or set the
variable yourself:

**Quote the value in `local.env`.** The path has spaces in it, and an
unquoted one is word-split by `.` -- `set -a; . ./local.env` reports
`Drive/External: No such file or directory` and leaves the variable unset,
so the run silently falls back to the samples, which is the exact trap
this file exists to close.

```sh
# local.env
NEST3D_PARTS="X:/dir with spaces/*.step"
```

```sh
set -a; . ./local.env; set +a          # bash
```
```powershell
Get-Content local.env | % { $k,$v = $_ -split '=',2
                            Set-Item "env:$k" ($v -replace '^"|"$') }
```

If `local.env` is missing on a new machine, the parts are on Google Drive and
the path is recorded in `results_glass/packing.json` under each part's `source`
key (that directory is gitignored but present on machines that have run them).
On Windows use the drive-letter form `X:/dir/*.step`; an MSYS `/x/dir` path
matches nothing in Python's `glob`.

## What has already been ruled out

Do not re-derive these -- all four are in README.md with their measurements,
under "Things that were tried and are not here": a bigger settle window, the
wall push, re-orienting during the settle (`--settle-orient`, off by default),
and feeding the settled box back as a container target. The GPU case for the
placement correlation is measured and declined there too, with the numbers.

The reason they all fail is one fact, from `tools/face_report.py`: after
settling, the pile is in wall-to-wall contact along every axis, so any rigid
inward shift grows the far face by exactly what it gains. Only moves that change
*relative* geometry can help.

## Verifying a change to the packer

`tests/test_nest3d.py` takes the packed result back to the triangle meshes and
runs exact boolean intersections on every pair. Anything that moves parts must
keep that passing -- the no-overlap guarantee is the property this tool is built
on. `tools/verify_orient.py` does the same for settled arrangements
specifically. Both need `rtree` and `manifold3d`.
